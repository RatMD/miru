# Floating App Bar

`FloatingAppBar` provides geometry, transparent cutouts, action segments and transitions. Applications provide shared `Button` / `ButtonAction` components through slots and keep ownership of routes, menus, permissions, translations, scanner state and notification counts. No application routes or stores are part of this component.

## Default circular layout

Defaults are `variant="five"`, `shape="circle"`, `appearance="solid"`, `orientation="horizontal"` and `fixed=true`. The primary remains a 68 × 68px circle. The panels remain 52px tall, share its vertical center, use a 43px circular cutout and fill each action segment on hover/press. Disabled actions stay visible and gray. Solid primary colors come from the slotted Button variant, so a green confirmation Button keeps working.

```vue
<FloatingAppBar :label="labels.navigation">
  <template #left>
    <Button variant="ghost" icon-only :aria-label="labels.home" @click="goHome"><HomeIcon /></Button>
    <Button variant="ghost" icon-only :disabled="!canGoBack" :aria-label="labels.back" @click="goBack"><BackIcon /></Button>
  </template>
  <template #primary>
    <Button variant="primary" icon-only :aria-label="labels.scan" @click="openScanner"><ScanIcon /></Button>
  </template>
  <template #right>
    <NotificationsTrigger />
    <ProfileTrigger />
  </template>
</FloatingAppBar>
```

The host must reserve scroll space **outside** the content card. `--ui-floating-app-bar-clearance` defaults to `7rem`; add the bottom safe-area inset. A vertical bar needs right-side clearance instead. Visibility breakpoints also belong to the application.

## Hexagon shape and gradients

Set `bordered=false` for borderless panels. The default is `true`, adding a thin border.

`shape="rounded-hexagon"` uses a rounded SVG path. Its 200 × 182 viewBox fits proportionally inside a 72px square. Each panel subtracts the same SVG enlarged to 92px using `mask-composite: exclude`. The opening is actually transparent; there is no painted border behind the primary.

Use `appearance="gradient"` with `gradientTone`: `primary` (indigo/purple), `success` (teal/lime), `danger` (red/fuchsia), `warning` (orange/amber), or `info` (sky/cyan). The gradients use a 135° angle. The default appearance uses solid buttons.

```vue
<FloatingAppBar
    :label="labels.navigation"
    variant="three"
    shape="rounded-hexagon"
    appearance="gradient"
    :bordered="false"
    gradient-tone="success"
    orientation="auto"
    auxiliary-position="edge"
    :transition-key="workflowStep">
  <template #left><Button variant="ghost" icon-only :aria-label="labels.back" @click="previous"><BackIcon /></Button></template>
  <template #primary><Button variant="success" icon-only :aria-label="labels.confirm" @click="confirm"><CheckIcon /></Button></template>
  <template #right><Button variant="ghost" icon-only :aria-label="labels.camera" @click="scan"><CameraIcon /></Button></template>
  <template #auxiliary-start><Button variant="danger" icon-only :aria-label="labels.cancel" @click="cancel"><CloseIcon /></Button></template>
</FloatingAppBar>
```

## Layouts and auxiliary actions

The preview toolbar exposes **Five Actions**, **Three Actions** and **Primary Action**. The last two layouts independently toggle **Left Button** and **Right Button**, including neither, either, or both. Five Actions hides these extra buttons while remembering their choices for the other layouts.

**Primary Color**, **Left Button Color** and **Right Button Color** are independent. Side color controls appear only while their extra button is enabled. These controls apply to both solid colors and gradient appearances. In application code, pass the primary gradient via `gradientTone`, and each auxiliary color via its slotted `Button`'s `variant`; auxiliary `primary` uses its own indigo/purple palette rather than inheriting a differently colored primary action.

| Prop / slot                         | Purpose                                                                       |
| ----------------------------------- | ----------------------------------------------------------------------------- |
| `variant="five"`                    | Two left actions, primary, two right actions.                                 |
| `variant="three"`                   | One action on each side of primary.                                           |
| `variant="primary"`                 | Primary only; side slots are not rendered.                                    |
| `auxiliary-start` / `auxiliary-end` | Additional 40px actions outside the panels; also available with primary-only. |
| `auxiliaryPosition="adjacent"`      | Additional actions immediately before/after the bar.                          |
| `auxiliaryPosition="edge"`          | Actions at the viewport edges in portrait, above/below the bar in landscape.  |

The host supplies the documented number of side actions. An absent optional action should remain a disabled Button if its place must be preserved. When grouping buttons in a host component, mark its root with `data-floating-app-bar-group` so the group participates in equal-width segments. `data-floating-app-bar-icon-offset` shifts just an icon 2px away from the center cutout: left in the left panel, right in the right panel, preserving its click target.

## Orientation and transitions

**White Page** renders the bar on a white mock page with a subtle frame border. Use the **White Page** and **Bottom Shadow** toolbar toggles to compare backgrounds and separation. The pointer-transparent shadow fades upward from the bottom in portrait and inward from the right in landscape; it remains behind the interactive bar.

**Auto Orientation** responds to the actual Storybook viewport, but its bar remains positioned inside the mock frame in Canvas and Docs. Manual rotation is also available; changing the actual viewport orientation restores automatic detection. The component's production `fixed` mode is unchanged.

Wrap an icon and its count badge in `data-floating-app-bar-glyph` so they counter-rotate as one unit. Position the badge relative to this group, not relative to the full button segment. Both the number and its top-right position then remain upright in landscape. Use `data-floating-app-bar-upright` for an isolated non-icon element that should counter-rotate on its own.

```vue
<Button
    variant="ghost"
    icon-only
    :aria-label="labels.notifications"
    data-floating-app-bar-icon-offset>
  <span data-floating-app-bar-glyph class="size-5">
    <BellIcon class="size-5" />
    <span class="absolute -top-1.5 -right-1.5 rounded-full bg-danger-600 px-1 text-[10px] text-white">{{ unread }}</span>
  </span>
</Button>
```

The optical offset follows the bar's axis: in portrait the inner left icon moves 2px left and the inner right icon 2px right; in landscape the upper inner icon moves 2px up and the lower inner icon 2px down. The hit areas do not move.

`orientation="horizontal"` positions the bar horizontally. `vertical` rotates the bar 90° and counter-rotates icons. `auto` responds to the actual viewport's orientation, moving a fixed bar from bottom-center to right-center. Position, width, rotation and icon rotation animate for 320ms. A 220ms spring-like exit/enter transition runs when the layout changes; use `transitionKey` for changes within one layout. Slot handlers and reactive disabled/loading states remain the host's responsibility.

Keep the same component instance during orientation changes. Do not key the whole component by orientation; doing so would replace it and prevent the position animation. Set `animated=false` to disable motion. The component respects `prefers-reduced-motion` independently of this prop.

The **Animated Switching** example cycles five → three → primary and changes orientation after a full cycle. Pause it to inspect any state. Other examples provide manual layout/rotation controls. The simulated device frame uses explicit orientation props; **Auto Orientation** demonstrates real viewport detection. Resize its Canvas/iframe between portrait and landscape. Storybook's English/German toolbar translates demo controls and action labels.

`fixed=false` supports a bar inside a dialog or a bounded preview. The host then positions the root. Preview-only `--ui-floating-app-bar-viewport-half-width` lets edge auxiliaries use an embedded frame's width rather than `50vw`; production fixed bars need no override.

## Shared state controller

Use `provideFloatingAppBar` once in a layout and `useFloatingAppBar` in descendant pages. State is isolated per provider/application without Pinia or module-global mutable state. The **State Controller** story demonstrates five-action navigation → three-action input → primary-only camera → input → navigation.

```ts
// Layout setup
import { provideFloatingAppBar } from '@rat.md/miru/composables';
const bar = provideFloatingAppBar(defaultConfig);
const { current, transitionKey } = bar;

// Descendant page setup: register on mount, release automatically on scope disposal.
import { useFloatingAppBar } from '@rat.md/miru/composables';
const pageBar = useFloatingAppBar(() => pageConfig.value);

// Temporary workflow: call the release handle OR pop(), not both.
const closeCamera = pageBar.push(cameraConfig);
closeCamera();
```

Bind `current.variant`, its visual configuration and actions into `FloatingAppBar` slots and pass the controller's `transitionKey` to the component. Resolve labels/disabled/loading with `toValue`, and icons with `unref` so functional Vue components are not called as getters. Labels are localized strings/getters from the host. Reactive fields remain live; the controller does not render or execute actions, navigate routes, open drawers or manage a scanner.

| Method         | Behavior                                                                  |
| -------------- | ------------------------------------------------------------------------- |
| `set(config)`  | Replace page/base state; discard temporary layers from the previous page. |
| `push(config)` | Add a layer and return its idempotent release handle.                     |
| `pop()`        | Remove the top layer and reveal the preceding one.                        |
| `clear()`      | Remove all layers and set the current configuration to null.              |
| `reset()`      | Restore the initial configuration and clear temporary layers.             |

An older page can release its own layer without removing a newer overlay or resurrecting an already disposed page. `useFloatingAppBar(config)` performs this ownership-based cleanup automatically. `createFloatingAppBarController(initial)` supports explicit adapters without injection. Do not share one factory instance globally across independent apps or SSR requests.

The controller changes state; the component animates it. A set/push/pop or reactive layout change changes `transitionKey`. Label, disabled and loading changes preserve it, so typing or validation does not exchange the bar.

Scanner state, navigation/profile/notification triggers and routing remain application responsibilities when adopting this controller.

## Application migration

Map menu layouts to `five`, simple layouts to `three`, and wizard layouts to `three` plus `auxiliary-start`. Keep navigation/profile triggers, store stacks, permissions and workflow callbacks in the host application. The separate top-corner menu trigger used outside the original menu layout remains a host control. Compare real touch devices, keyboard focus, safe areas and landscape content clearance before migration.
